# D100. 详情栏在接近自动压缩点时提供手动压缩，按宿主的 /compact 命令执行

## 背景

上下文一节报出占用与窗口，读者据此判断这条会话还能走多远，却无法在栏里先压缩一次。压缩能力在宿主里是可选 seam：`ctx.compaction` 是 Service Definition，`dsh-compaction-basic` 是默认后端，`/compact` 是面向读者的命令。

这条 seam 在桌面 profile 里被装进一个隔离组（`cordis:group` 加上 `isolate: { compaction: true }`），组外的上下文读不到它：插件从根上下文取 `ctx.compaction` 一律为空，从 agent 自己的作用域里取同样为空。隔离是宿主有意的设计，插件照着读只会得到「没有这个能力」。

自动压缩的触发点由后端策略算出：窗口乘阈值比例（默认 0.8），再与「窗口减去请求自身的输出预留与 64 Ki 的 headroom」取较小值。策略挂在后端实例上，隔离组之外同样读不到。

## 决定

- 上下文一节在接近自动压缩点时多一行：左侧写「距离自动压缩还有 N」，右侧一个「压缩会话」按钮。距离在阈值之前不到窗口两成时这一行才出现，越过阈值仍然保留——那时宿主会在下一个步骤边界自行压缩，读者也可能想立刻压。离得远时整行不出现。
- 阈值按后端自己的默认值计算：窗口 × 0.8，与「窗口 − 输出预留 − 65,536」取较小值，输出预留取最近一次请求头声明的 maxTokens。这两个常数是后端的默认策略，放在 `packages/contracts/src/compaction.ts`；一个把策略放开给插件读的宿主，其读到的比例、headroom 与模型级覆盖优先于默认值。
- 按下按钮执行宿主自己的 `/compact` 命令：宿主半边从 agent 注册表取这条会话的活 agent，再通过命令注册表执行一行 `/compact`，与读者在输入框里敲这条命令走同一条通道——准入、压缩锁、摘要与持久化都在宿主那一侧完成。插件不实现压缩，也不猜压缩范围。
- 命令的答复原样带回：成功时栏里写「已压缩」，失败的句子作为提示；宿主没有这条命令、或这条会话没有活 agent 时，栏里按类别说明。
- 一次只允许一个请求在飞，按钮在请求期间禁用并写「正在压缩…」。压缩写入的是宿主的事件流，面板的下一轮轮询自然读到新的占用与分项，距离随之变大，这一行自己退场。
- 面板值里的 `context.compaction.thresholdTokens` 由宿主半边折叠时算出；宿主没有窗口或没有可用策略时不带这个字段，栏里也就没有这一行。

## 后果

- 手动压缩与自动压缩用的是同一套策略与同一条 seam，两者不会给出不同的结果；插件拿不到策略时退回后端的默认常数值，这一处是估算，图例下方那行小字已经说明分项与阈值都是估算值。
- 压缩会改写会话的历史，操作不可撤销；按钮就是一次点击，没有二次确认，与宿主自己的 `/compact` 一致。
- 宿主若把压缩能力开放给插件（例如提供可读的策略或直接调用入口），改为读那个入口，删掉默认常数与命令行的间接调用。
- 后端默认值若随宿主版本改变，这一处会与真实触发点出现偏差；届时更新 `DEFAULT_COMPACTION_POLICY` 一处即可。

## 重审条件

- 宿主提供插件可读的压缩策略或压缩触发投影时，改为读投影，删掉默认常数。
- 宿主提供插件可直接调用的压缩入口时，改为调用入口，删掉命令行的间接调用。
