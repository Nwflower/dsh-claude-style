# D99. 上下文分项按发送给模型的内容计价，占用仍取服务商读数

细则不取代 D94 对详情栏本身的决定，只更换它那一节分项的计价来源与拆分方式。

## 背景

详情栏的上下文一节原先借用宿主的 `contextBreakdown`：系统提示、工具定义与对话总量由宿主的计量投影给出，指令文件、技能与其他上下文再由宿主的 `estimateMessage` 单独估价，MCP 份额按工具 JSON 长度的比例切分。宿主这套计量是「字符数 ÷ 4」，每个块加 4、每条消息再加 4，按字符密度折算。

两处代价因此落到分项上。一是中文、标点、代码与英文单词在同一把尺子上同价，而分词器对它们的花费相差数倍，中文会话的对话份额被摊薄；二是两份尺子（宿主的聚合投影与本插件的估价）混用，谁的份额被放大取决于谁的字数更多，与内容本身无关。另有一处不是尺子的问题：先前参与的只有带来源标注的注入消息，其余对话挤在同一行，读者看不出对话里是谁在占地方。

## 决定

- 分项全部改读宿主会话日志里实际发送的内容：保留的消息内容块、请求头里的工具定义、系统提示本身。页面上的可见文本不参与分项，流式回答的实时估算只服务于底部读数。
- 计价只有一处实现，在 `packages/contracts/src/tokens.ts`：文本按字符类别分段计价（中文、标记、拉丁单词、数字、空白、标点各按分词器的价格），每条消息按内容块分别定价再加角色与块的框架开销，图片按像素格换算并在单图上限处封顶，未知块按它被发送的 JSON 结构定价。宿主半边与浏览器半边都调这一处，宿主的 `tokenMeter` 不再参与。
- 折叠随事件增量进行：消息到达时定价一次并计入它所属类别的累计，替换范围（压缩、裁剪）时把范围内的价格扣回，因此长会话里每条事件只花一次计价。工具定义在请求头到达时计价，名字以 `mcp__` 开头的单列为 MCP，其余为系统工具。
- 类别沿用本插件原有的分项，并按来源细分对话与注入：用户消息、助手消息、工具结果各成一行，技能目录与技能调用算技能，带指令文件标注的消息算指令文件，其余带来源的注入算其他上下文。正文以 `<skill_content` 开头的工具结果算技能，因为宿主的技能工具只把技能正文交给日志，不带来源标注。
- 系统提示只把最新一条算作系统提示；被新提示顶替但仍留在上下文里的旧提示算其他上下文。
- 占用与窗口仍是服务商的读数，分项按各自价格的比例分配这份占用，各项之和与占用相等。图例的百分比以整个上下文窗口为分母。
- 分项按分配到的代币数从大到小排列，色块自左向右与之同序，读完图例的顺序就是读色块的顺序；大小相同的项保持类别本身的顺序。剩余空间不参与排序，固定在最后一行。
- 对话的三行用可分辨的三色：用户消息为蓝，助手消息为紫，工具结果为青，与系统工具的橙、MCP 的绿、系统提示的黄各自分开。
- 全部八种分项色是同一个色调家族：同一主题下各自的感知明度相同（浅色 0.62、深色 0.72，按 OKLCH 计算），色相与彩度保持各自的身份，指令文件与技能、其他上下文用低彩度的灰调表示它们是注入文本。于是色条里没有哪一段比其他段更亮，类别只靠色相分辨，深浅两套主题各用自己的一档。

## 后果

- 分项之间的比例由内容本身决定，同一会话里中文、代码与英文混排的比例不再被字数摊平；占用总量与颜色条的总长仍等于服务商的读数。
- 一份估算器同时服务宿主半边与浏览器半边，页面文本的实时估算与详情栏的分项用同一套价格，两处不再出现同内容不同价。
- 宿主若改变会话日志的内容块形状（新增块类型），未知块按 JSON 结构价参与分配，不会使整个分项缺席；这类块的份额会偏低，需要时在计价表里补一条。
- 图片按像素计价，与请求侧对图片的独立定价不再一致；一处是估算，一处是账单，两者不追求相等。
- 分项不再依赖宿主的 `contextBreakdown` 投影；宿主不提供该投影时，分项照常给出。

## 重审条件

- 宿主提供按类别归因的上下文投影（系统提示、工具、消息分别给出读数）时，改为读该投影，删掉本插件的折叠与计价。
- 服务商公布的分词价格与这里的字符类别价格明显偏离（新模型换了分词器）时，更新 `packages/contracts/src/tokens.ts` 的常数，两处的估算同时跟随。
