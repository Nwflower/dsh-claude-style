# D109. 钠改写只适配宿主，不读版本

- **取代**：D78

## 背景

宿主的对话流样式里有几条间距规则用 `:has()` 判断一个流条目是否为空，再经兄弟组合子把这一判断传给其后的条目；这几条规则的主体没有类名、标签或属性可供浏览器分桶，页面上每个元素都要拿它去试，长会话里样式重算的单价随之上涨。宿主没有为这类规则提供开关。被取代的决策为此建立了就地改写，并把适配表按成员组织：每个成员写明版本从哪里读（宿主引导图或 profile 的 bundle 列表）、从哪一版开始适配，版本读不到或低于起始值的成员不参与改写。

插件的宿主下限此后提高到 0.2.2-rc.3，高于表里唯一成员（宿主）的起始版本 0.2.2-alpha.3：版本比较对任何能装载插件的宿主恒为通过。bundle 成员类型自建立起没有任何成员，为它保留的 profile 列表读取与失败分支同样无人触发。宿主 rc.5 的对话流样式里，上述不可分桶的间距规则仍在，改写要解决的问题没有消失。

## 决定

- 适配表只持有宿主的适配项：每个适配项写明样式表（加载器标在样式节点上的包名与路径）、它认得的规则，以及维护兜底标记的脚本。成员不声明版本来源与起始版本，引擎不读宿主版本，也不读 profile 的 bundle 列表。
- 开关打开时，适配表里登记的规则在原样式表里就地改写选择器，让浏览器能给它们分桶；关闭时选择器原样写回、皮肤写的标记全部撤下，页面回到宿主自己的样子。
- 表里写的是整条选择器：浏览器序列化出来的样子，带哈希的类名按角色占位，第一次出现时捕获，之后必须是同一个类名。差一个字就匹配不上，规则保持原样；宿主改了规则，页面上留下的就是宿主自己的规则。
- 改写只动主体：把它按宿主在创建元素时就写上的键展开成并列的几支，浏览器按这些键分桶，只拿这些元素去试。元素一插入就带着键，宿主在同一个任务里插入节点又同步读布局时，改写后的规则与原规则读到的是同一组元素。规则里的结构判断原样留给浏览器实时判定。
- 宿主或别的插件放进流里的其他种类，由脚本写在流容器每个子元素上的标记兜底：它是并列的最后一支，在变化观察的回调里写上。
- 替换与原规则等价：对同一棵树命中同一组元素，优先级相同。为补上键占去的那一份优先级，并列的否定条件合进同一个 `:not()`，它只计其中最重的一项。
- 开关默认关闭，偏好的初值是「未决定」。读到用户设置之后的探测里，适配表一有规则命中，就替用户打开；用户拨过一次开关，探测不再改它。
- 设置项的小字报告生效中的规则条数，悬停按成员列出每一条规则的来源与声明；成员行不带版本。

## 后果

- 开关打开时，宿主的样式表与它作者写下的样子不再一一对应；排查样式问题前先关掉开关。
- 适配一条新规则要同时写出它的整条选择器、替换写法与它依赖的宿主契约，并由规格核对两者在同一棵树上命中同一组元素、在层叠里分量相同。
- 宿主每次改动这些规则，表里对应的一条就失效，要按新的写法重新登记；宿主给流里加了新种类的子元素，要把它的键补进主体的分支，否则它只能等兜底标记。
- 改写作用在样式表对象上，同一份样式被重新注入时改写随旧对象一起丢失，皮肤要监视 `<head>` 并对新对象重新匹配。
- 表里加一个插件成员，或重新引入版本判定，需要另写决策：恒为通过的版本门读一次引导图、维护一条无人触发的比较路径，而扩展真正到来时需要的判定形状未必是这一个。
- 放弃的方案：在皮肤样式表里写更高优先级的规则盖住宿主的声明——浏览器照样要求值原规则，开销没有减少。放弃的方案：删除原规则、插入改写后的副本——宿主自己的增删会让记下的位置失效。放弃的方案：只用脚本写的标记收窄主体——标记要等变化观察的回调才更新，宿主在回合结束时撤下运行行、插入新条目后在同一个任务里读布局，读到的内容比原规则下短，滚动位置被浏览器夹回一截。

## 重审条件

- 宿主修掉这些规则，或为流条目提供可分桶的属性时，对应的适配项删除。
- 浏览器对这类结构选择器的匹配与失效成本降到与普通属性选择器相当时，整个功能删除。
