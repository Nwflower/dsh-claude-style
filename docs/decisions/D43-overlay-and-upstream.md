# D43. 覆盖层定位与等待扩展点

- **状态**：已实施
- **分组**：宿主边界
- **关联**：取代 D2；D3、D19、D39、D41、D44
- **现状**：一切效果靠浏览器端的 CSS 覆盖与 DOM 覆盖实现，不修改 DSH 引擎、apiproxy 与官方 UI 包；宿主目前不接受外部 issue 与 PR，扩展点只能等宿主自己开

## 决定

- 插件是盖在宿主上的一层：宿主没有正式扩展点的地方，效果以 CSS 覆盖与 DOM 覆盖实现，并把这些覆盖依赖的假设写进契约模块（D44）。
- 扩展点不由本仓库推动：宿主不接受外部 issue 与 pull request，等宿主自己开放。等待期间的做法：
  - 缺扩展点的几处覆盖（跟随策略、提交生命周期、吉祥物插槽、插件资产与动态分块、官方 UI 的稳定 `data-*`）各写一份文档留在 `.debug/upstream/`，写清现在靠什么细节撑着、坏了会怎样、想要的入口是什么；草稿是内部记录，不对外提交，也不进版本管理。
  - 宿主放出对应能力时，该处覆盖改为接入宿主，并从契约模块里删掉被取代的假设（D44）。
- 宿主半边只做浏览器做不到的事：提供模型文案、字体、吉祥物帧图与其他资源、系统用户名、HDSL 契约、用量汇总、会话内容搜索、删除会话这些路由（D11、D22），以及设置表单用的 `Config`（D10）。

## 理由

- 覆盖层的正确性取决于宿主没有承诺过的内部细节；今天能做到的效果，宿主改一次版就可能失效，最有效的稳定手段是宿主自己承诺，而这件事不由本仓库决定。
- 把每处覆盖的代价写清楚，宿主开放能力时可以立刻对照着改，不必重新推导一遍。

## 代价

- 覆盖与真接入的差别只能靠契约测试（D44）与端到端通道（D45）兜住；宿主升级要跑一遍才知道哪条假设失效了。

## 重审条件

- 宿主开始接受外部 issue 与 PR，或开放完整的主题 API 时，恢复「向上游提交扩展点」这条路。
