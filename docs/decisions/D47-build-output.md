# D47. 构建产物不进主分支，发布分支提供 git 安装

- **状态**：部分实施
- **分组**：构建与源码
- **关联**：D36、D45
- **现状**：`lib/` 已加入 `.gitignore` 并从版本管理里移出；`scripts/dist-branch.mjs` 自己跑一遍构建、把 npm 会发布的同一份文件写成一个孤立的 `dist` 提交，并把版本标签移到该提交上（两条安装路径同一份产物），`.github/workflows/release.yml` 在标签推送后跑门、发布 npm 并推送该分支；整条发布路径已在临时克隆里走过一遍（汇编变更记录、改版本、打标签、写分支、核对产物与标签指向），首次推送与 README 的 GitHub 安装行改指 `#dist` 待这次发版进行

## 决定

- `lib/`（以及 D46 之后各包的构建输出）在 `master` 上加入 `.gitignore`，不再提交。
- 持续集成负责构建；发版时由持续集成构建、打包并发布到 npm，发布的内容与通过测试的构建是同一份。
- 同一次发版，持续集成把与 npm 包内容相同的文件提交到 `dist` 分支，并把版本标签移到那个提交上（发布工作流由标签推送触发，标签先落在发版提交上）：按标签安装与按 npm 安装拿到的是同一份已构建的包。`dist` 分支只由持续集成写入。
- 写 `dist` 的那一步自己先构建：`lib/` 不在版本管理里，干净检出没有它，只执行打包会写出一个 `main` 指向缺失文件的包。

## 理由

- 被跟踪却只在发版时更新的产物既不是源码，也不能保证是最新的，平时只会以「改过的文件」出现在工作区里。
- DSH 用 pnpm 安装 git 上的插件，带构建脚本的包要读者先批准构建、再下载开发依赖；装一个已经构建好的分支，读者不需要这两步。

## 代价

- 无法再从 `master` 的某个提交直接拿到可用的产物，必须构建，或从 npm、`dist` 分支安装。
- 发版流程多一步推送分支，持续集成需要仓库的写权限。

## 重审条件

- DSH 的插件管理器能在安装 git 上的插件时自动执行构建，或插件市场改为只从 npm 安装时，删除 `dist` 分支。
