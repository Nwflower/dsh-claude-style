# D44. 宿主契约模块与契约测试

- **状态**：部分实施
- **分组**：宿主边界
- **关联**：承接 D3、D19 与 D32 的聊天区契约表；D42、D43、D45
- **现状**：契约模块是 `src/contracts/`：`dom.ts` 是皮肤依赖的宿主选择器与属性的唯一定义处（66 条），`table.ts` 是每条 id、它是什么、谁在读、核对过的宿主构建与核对方式，`timing.ts` 是宿主与皮肤之间的时序假设，每条写明它依赖的顺序、坏了会怎样、以及由哪个检查持有（通道场景或单元测试，构建核对两者都在），`services.ts` 是宿主服务与值的形状：只声明皮肤真正读到的成员，`core/host.ts` 的访问器按它返回。功能清单用 `contracts` 字段登记自己读过哪些条目，构建检查三者一致。端到端通道的 `contract` 场景走一遍空页、提交、流式、落定、菜单与暗色，逐条核对表里的条目（D45）。各功能内部仍有多处 `HostValue`（85 处注解），逐处改成具名形状是这条决策剩下的最后一步

## 决定

- 皮肤依赖的宿主选择器、属性、服务形状与时序假设集中成一个有类型的契约模块，每条注明在哪个宿主版本上验证过、哪些功能依赖它（功能清单里列出，D42）。
- 契约测试用锁定版本的真实宿主客户端包挂载真实组件来跑，逐条核对契约模块里的假设，取代手搭的替代页面。
- 宿主升级时先跑契约测试，失效的假设逐条列出，再改对应功能。
- 时序假设同样写成契约并测试，例如「宿主在挂上消息列时新建 ResizeObserver、在其中把位置写到最底」（D32）。

## 实施

- `src/contracts/dom.ts` 只放字面：皮肤读的每个宿主选择器与属性在这里定义一次。
- `src/contracts/table.ts` 是同一份契约的表：`id`、`value`（引用上面的字面）、`probe`（在哪个页面状态、按哪种方式核对）、`use`（它是什么、谁在读），表的头里写着这些条目核对过的宿主构建。表是构建与测试数据，不进产物；浏览器半边只带字面本身。
- `src/contracts/timing.ts` 是时序那一半：`assumption`（宿主的工作顺序）、`use`（皮肤拿它做什么、坏了会怎样）、`checks`（`scenario:<通道场景>` 或 `test:<测试文件>`）。构建核对场景名在通道里存在、测试文件存在，通道启动时反过来核对它的场景名与表里一致。
- `src/contracts/services.ts` 是服务那一半：宿主服务（`sessions`、`uiSession`、`uiConversation`、`locale`）与它们的值（会话、聊天快照、轮次、步骤、投影面）各一个接口，只声明皮肤读到的成员，每个成员注明读来做什么；宿主不挂载的服务由 `ctx.get` 返回 `undefined`，因此类型上可能缺席，读取处照旧按「可能没有」写（D12）。`core/host.ts` 的访问器按这些接口返回，各功能内部沿用的 `HostValue` 是尚未收进来的那些值。
- 功能清单的 `contracts` 字段登记该功能读过的条目 id；构建检查：`dom.ts` 的每个字面在表里有条目、表里的 id 不重复、清单里的 id 都存在、每条要么被至少一个清单认领、要么标着 `owner: 'core'`（只由插件的核心与共享模块读的少数几条）。
- 迁移分步：聊天区、外壳、核心与各功能的选择器都已收进模块，时序假设已成表，服务形状已有接口且核心访问器按它返回；剩下的是各功能内部 85 处 `HostValue` 注解逐处换成具名形状。

## 理由

- 替代页面只能复现作者已经知道的结构，复现不了真实宿主的时序；聊天区跟随与宿主的争抢在替代页面上一直是绿的。
- 契约集中之后，宿主升级的影响面一眼可见。

## 代价

- 契约测试要能装上并挂载真实宿主包，环境比替代页面重；锁定的宿主版本要随支持范围更新。
- 加一条宿主选择器要同时改模块、表与清单三处，构建会盯着，但这三处是手工维护的。

## 重审条件

- 宿主为插件提供官方的契约或测试工具包时改用宿主的。
